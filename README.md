## 产品简介

### 它是什么

一个部署在您自己服务器上的农场自动化助手，由两部分组成：

- **core 后端**：以子进程 Worker 隔离运行每个游戏账号，通过微信小游戏协议与服务器通信，执行挂机策略
- **web 面板**：Vue 3 单页应用，由后端托管，提供账号管理、策略配置、实时状态与日志查看

### 能做什么

| 能力 | 说明 |
| --- | --- |
| 多账号挂机 | 每个账号独立进程运行，互不干扰；掉线自动重登；支持抓包 Code 与微信扫码两种登录方式 |
| 农场自动化 | 收获、种植、浇水、除草、除虫、施肥、土地升级全流程自动化，策略可按账号配置 |
| 好友自动化 | 偷菜、帮忙、捣乱合并为单次访问，支持黑名单、安静时段与互动上限 |
| 活动自动化 | 奶茶热销中、快乐不独享、节令日历等活动的全流程自动化，单步容错，详见[活动自动化](#活动自动化) |
| 经营分析 | 作物收益分析、策略预览、背包估值、商城与神秘商人价格查询 |
| 事件推送 | 基于 pushoo 的实例级通知；断线先等 150 秒自动重登，重登失败才提醒，恢复在线不打扰 |

### 适用场景与边界

适用于拥有 QQ 农场微信端账号、希望减少重复操作的个人用户。本项目不提供多用户体系，不适合作为多人共用服务对外运营。

> [!WARNING]
> 本项目仅供学习与研究用途。使用本工具可能违反游戏服务条款，由此产生的一切后果由使用者自行承担。

## 快速开始

### 环境要求

| 运行方式 | 要求 |
| --- | --- |
| 源码运行 | Node.js 20.19 或以上、pnpm 10 或以上 |

推荐通过 Corepack 启用项目指定版本的 pnpm：

```bash
corepack enable
pnpm --version
```

### 步骤一：获取并构建

```bash
git clone https://github.com/lengxiaobingege/qq-farm-bot.git
cd qq-farm-bot
pnpm install
pnpm dev
```

`pnpm dev` 会先构建前端，再启动后端。Windows、Linux、macOS 均可使用。

### 步骤二：登录管理面板

1. 服务首次启动只创建管理员账号 `admin`，密码为空。
2. 用浏览器打开管理面板：**本机访问**用 `http://localhost:3000`；**局域网或公网访问**用部署机的 `http://<主机地址>:3000`（`3000` 是对外统一入口）。登录页自动切换为「首次使用 · 设置管理员密码」。后端直连地址 `http://localhost:3007` 仅供本机排障使用，日常无需关心。
3. 自行输入密码并确认；也可以单击「生成随机密码」按钮生成 16 位强密码并自动填入，生成后请立即保存或复制。
4. 提交后自动登录进入面板。

密码要求：至少 8 位，且包含大写字母、小写字母、数字、特殊符号中的至少 3 类。

### 步骤三：添加游戏账号

1. 进入设置页，添加游戏账号（微信扫码或抓包 Code 登录）。
2. 启用账号，系统为其启动独立 Worker。
3. 在自动化配置中勾选农场、好友、活动等策略。

### 步骤四：验证运行

1. 面板概览页应显示账号在线状态与角色 ID。
2. 实时日志应出现任务调度记录（如收获、种植、活动任务）。
3. 如配置了事件推送，手动停用账号网络后约 2 分钟内应能收到掉线通知（系统先等 150 秒自动重登，重登成功则不推送）。

### 后台常驻运行（Linux）

```bash
bash ./start.sh              # 缺依赖或代码变化时自动安装并增量重建（同时拉起看门狗）
bash ./start.sh --rebuild    # 忽略缓存完整重建
tail -f app_dev.log          # 查看日志
bash ./stop.sh               # 停止服务（先停看门狗，再停主进程与 3000 转发）

bash ./watchdog.sh status    # 查看看门狗状态与最近记录
bash ./watchdog.sh start     # 单独启动看门狗（幂等）
bash ./watchdog.sh stop      # 单独停止看门狗
tail -f watchdog.log         # 看门狗的检查与重启记录

bash ./preflight.sh          # 交付前自检：单实例、双口、转发一致性、看门狗心跳、日志、崩溃转储、账号在线
bash ./preflight.sh --full   # 额外跑一遍 core 测试套件
```

看门狗每 60 秒检查一次，只在确认主进程真的不在时才动手：

| 场景 | 行为 |
| --- | --- |
| 主进程正常、3007 可用 | 不做任何事；顺带检查 3000 转发，断了就重建 |
| 主进程不在、3007 空闲 | 调 `start.sh` 拉起，最多连续 3 次 |
| 主进程不在、3007 被本项目遗留进程占用 | 只补写 pid 文件，不重启（避免双实例重复购买） |
| 3007 被其它程序占用 | 一律不抢占，记录 `foreign(...)` 后跳过 |
| 连续 3 次拉起或健康检查失败 | 停止自动拉起，并推送一条「自动重启失败」告警 |
| 进程活着但 3007 连续 3 次无响应 | 先 TERM 再 KILL，然后重新拉起 |

`start.sh` 每次启动会把上一轮日志改名成 `app_dev.log.prev`（只留一份），因此自动重启后仍能回看崩溃或断线现场。`start.sh` 自身带目录锁，看门狗与手动启动同时触发时只有一个能继续，避免双实例重复购买。`stop.sh` 除 pid 文件外，还会按「cwd + argv」精确清理没有登记的手工实例。

> [!NOTE]
> 看门狗是普通后台进程，和主服务同生命周期。容器/沙箱整体休眠时它也会一起停，醒来后需要手动 `bash ./start.sh`；它只能救“进程自己挂了”，救不了“整机没了”。

> [!TIP]
> 仍然建议用 `start.sh` 后台启动：主进程现在会忽略 `SIGHUP`，关终端不再把进程带崩、也不再落近百 MB 的 core dump，但前台跑依旧有三处短板——日志只进终端不落文件、没有看门狗、终端被会话恢复重放时还会多起一个抢端口的实例。
>
> 也不要在终端里留 `PORT=3000 node core/client.js` 这类历史命令：终端会话恢复会重放它，起出一个绕开 `start.sh` 的野实例（不登记 pid、没有看门狗、也没有 3000→3007 转发）。现在有三层防护：① 主进程启动会探测 `PORT` 是否已被监听，已有实例就直接退出并写日志（`端口 N 已被占用，疑似已有实例在运行`）；② 编译产物若从前台交互终端直接启动会被**终端守卫拒绝**（提示改用 `start.sh`）——`start.sh` 经 `nohup setsid` 脱离终端并显式带放行标记，不受影响；③ `preflight.sh` 用「pid 文件不一致 / 3007 无响应 / 看门狗未运行」把它抓出来，`stop.sh` 按 cwd + argv 清理。
>
> 确需在前台直接运行编译产物调试时，设 `QQ_FARM_ALLOW_TTY=1` 即可放行守卫；开发态用 `pnpm dev`（tsx 跑源码）本就不受守卫影响。

### 常见问题

| 问题 | 处理方式 |
| --- | --- |
| 扫码登录后不久掉线 | 系统会自动通过 refreshToken 或 openid + accessToken 重获会话；若持续掉线，重新扫码即可 |
| 管理员密码遗忘 | 属服务器运维操作，需要文件系统访问权限，流程不在公开文档中说明，请妥善保管密码 |
| 端口被占用 | 对外入口固定 `3000`；后端直连端口 `3007` 可在 `.env` 的 `PORT` 中调整，`start.sh` 会自动重建到 `3000` 的转发 |
| 活动自动化没有执行 | 确认设置页「活动任务」自动化开关已启用；活动结束后对应条目会自动静默 |
| 想看某次协议交互细节 | 参考[项目文档](#项目文档)中对应专题文档与 tools 目录下的抓包分析脚本 |

## 功能说明

### 活动自动化

活动自动化代码位于 `core/src/services/activity-auto/`，每个活动一个独立文件，由调度器串行编排，避免并发请求触发网关限速。设计要点：

- **单步容错**：任一步骤失败（例如货币不足）只跳过该步骤，不中断整轮
- **错误去重**：同一活动的同一错误 30 分钟内不重复写日志，避免活动结束时刷屏
- **过期静默**：活动结束后对应自动化自动停止，不产生无效请求

| 活动 | 自动化流水线 |
| --- | --- |
| 奶茶热销中 | 领取收银台收益与工资 → 按店铺等级工位上限补雇员工（24 小时 → 12 小时 → 4 小时阶梯降档，有多少花多少）→ 加速收银台 → 升级店铺 → 制作饮品 → 涨薪互动 → 成长基金解锁与领取 |
| 快乐不独享 | 每日快乐值、每日首次分享、可领档位奖励 |
| 节令日历 | 节令开放当天自动执行一次（按北京时间记账）：领取奖励、本地题库答题（带题目变化防呆）、季度累计奖励 |

### 农场自动化

- 自动收获、种植、浇水、除草、除虫、铲除与土地升级
- 自动施肥、多季作物补肥、指定土地类型施肥、化肥自动购买
- 一键务农、种植、收获、铲除、全收等面板快捷操作
- 多套种植策略、背包种子优先级、作物黑名单与执行间隔可按账号配置
- 任务、免费礼包、分享奖励、会员礼包、月卡礼包、图鉴奖励等每日状态汇总，按天自动领取

### 牧场自动化

牧场模块已与上游同步，覆盖窝棚、动物、集市、图鉴、任务与背包全流程：

- **动物管理**：窝棚分组展示、幼崽补栏、健康与产出状态；一键喂养支持普通罐头与有机罐头按阶段配置，罐头桶没有可用时长时自动跳过本轮
- **集市与兑换**：松果、仓鼠集市按货币拆分独立开关，按到访通知排队兑换，避免并发抢占
- **图鉴**：牧场图鉴与巨型图鉴，支持一键已读、成熟后自动领奖
- **好友互动**：牧场好友巡查与偷取、按场景同步好友名单（优先显示昵称）、好友黑名单（服务端拒绝拜访的非好友自动拉黑）
- **背包与设施**：牧场背包出售、罐头与棚舍设施升级、商品货架自动更新
- **任务**：牧场成长任务自动完成，含打开好友面板等子任务

### 好友互动

- 自动访问好友、偷菜、帮忙浇水、除草除虫、放草放虫
- 巡查合并为单次访问：每位好友只进一次农场完成全部互动

### 图鉴与藏品

- 作物图鉴与超变图鉴的等级、进度、果实收藏状态一站式查看
- 超变图鉴依据 `Illustrated.json` 的 `param`/`type` 字段区分黄金果实、活动果实与装扮果实，不依赖名称推断
- 超变属性弹窗汇总当前生效加成与等级达成明细，移动端四列布局自适应

### 背包与交易

- 背包物品使用、出售与批量出售，按活动区间与过期时间智能判断可售状态
- 神秘商人活动商品、游戏商城价格折扣限购与购买
- 种子、果实、道具与作物收益数据查询

### 活动中心

- 活动列表协议统一展示当前与已结束活动；快照请求串行合并，避免占满游戏网关请求队列
- 千星游记（赛季通行证）、观星礼录（星座点亮）、星砂商店（兑换）、节令活动、鹊桥寄情（筑桥与赠礼）、雨落成诗（天气瓶与气象研究）等玩法页面

### Web 控制面板

- 概览、个人、活动、好友、分析、神秘商人、游戏商城、设置页面
- Socket.IO 实时状态与日志流，液态玻璃风格界面；PC 固定侧栏，移动端顶部栏与底部导航
- 设置页统一管理游戏账号、自动化策略、运行环境、管理员密码与事件通知

### 事件推送与掉线判定

- **断线不立刻喊**：连接断开后先挂起 150 秒，把这段时间让给自动重登；期间恢复在线则完全静默
- **真失败才推**：重登三次全失败、无可用会话、持续离线超时属于终态，立即推送，不再等窗口
- **兜底不漏**：既不成功也不失败（卡住）时，150 秒到期补一条
- **恢复才闭环**：真推过「已离线」的账号，恢复后再补一条「农场已恢复在线」；没推过的不补
- **登录不打扰**：扫码登录、服务重启、自动重登成功本身都不推送，登录提醒已从 worker 移除
- **不刷屏**：同账号同类掉线 10 分钟内只推一条；推送串行发送，失败重试一次
- **会话保活**：每小时整点刷新一次会话，成功不推送，失败才提醒
- **重启不误报**：`stop.sh` 先停 worker 再退主进程，worker 主动停止不进提醒流程，运维重启不会换来一条「已离线」

判定流程与参数说明见[事件推送与掉线判定](docs/event-notify.md)。

## 🔐 管理端安全设计

面板不设注册体系，全局仅一名超级管理员，账号固定为 `admin`。本章说明安全机制的设计原理与使用边界。

### 凭据模型

| 阶段 | 触发条件 | 行为 |
| --- | --- | --- |
| 未初始化 | `admin.json` 不存在或标记 `needsSetup` | 登录接口拒绝一切密码尝试，登录页自动切换为「设置管理员密码」表单 |
| 已初始化 | 首次设置完成 | 进入常规登录；设置接口永久失效，无法被再次调用覆盖凭据 |

设计取舍：

- **无预设密码、无默认密码、无后门**。从根上消除"部署后未及时改密"这一最常见的事故窗口，攻击者不存在可以猜的默认值。
- **明文密码永不落盘、不经网络回传**。首次设置时密码仅存在于浏览器到服务器的单次请求中，服务端只保存 PBKDF2 派生哈希（SHA-512、10 万次迭代、32 字节随机盐），此后没有任何命令或接口能读回密码。
- **登录页内置 16 位随机密码生成器**。基于浏览器 `crypto.getRandomValues` 密码学安全随机源，四类字符齐全，剔除易混淆字符 `0O1lI`，生成值自动填入并支持一键复制。
- **密码策略**：至少 8 位，且包含大写字母、小写字母、数字、特殊符号中的至少 3 类，拒绝常见弱口令字典。

### 防爆破与锁定

- 双层限流：每个 IP 每分钟最多 10 次请求；登录失败 5 次锁定该 IP 15 分钟，窗口自动过期清理
- 锁定按 IP 分桶而非全局锁账号：单一来源的暴力尝试不会把账号整体锁死形成拒绝服务，也无法通过更换用户名绕过
- 客户端 IP **默认只认 TCP 对端**：未配置 `TRUSTED_PROXY_IPS` 时，`X-Forwarded-For` / `X-Real-IP` / `CF-Connecting-IP` 一律忽略，伪造请求头无法换取新的限流桶
- 部署在 Nginx/Caddy/CLB 之后时，必须把**代理自身的真实 IP** 填入 `TRUSTED_PROXY_IPS`（逗号分隔，不要填网段）；Express 的 `trust proxy` 与本白名单联动，不填则按直连处理
- 登录成功与失败（含来源 IP）全部落日志，可审计

### 会话与设备验证

三道机制叠在一起，目标不是"绝对拦得住"，而是**让多出来的人既进不去、也藏不住**。

**1. 会话有生命周期（不再是永久令牌）**

| 参数 | 默认 | 环境变量 |
| --- | --- | --- |
| 滑动有效期（多久不用即失效） | 7 天 | `ADMIN_SESSION_TTL_MS` |
| 绝对有效期（签发后最迟重登） | 30 天 | `ADMIN_SESSION_MAX_MS` |

每次带令牌访问都会续期，但无论怎么续都不会越过绝对上限。落盘写操作按 5 分钟节流，不会变成每请求一次磁盘 IO。旧版 `admin-sessions.json`（只有令牌数组、无时间）首次启动时自动迁移为带生命周期的结构，不会一升级就把所有人踢下线。

**2. 单会话强制**

同一时间只允许一处登录。新登录会清空全部旧会话并断开旧连接的实时通道，且在新会话的通知里写明挤掉了几个。密码泄露时，对方一登录你就会立刻被踢下线——这本身就是一次硬报警。

**3. 新设备登录需微信验证码**

```
密码正确 → 该设备已受信任？ ── 是 ──→ 直接签发会话
              │否
              └→ 生成 6 位码 → 推送微信 → 登录页回填 → 校验通过才签发，并信任该设备 30 天
```

- 验证码 5 分钟有效、一次性、绑定设备标识与来源 IP，**错误 3 次即作废**；同 IP 最多同时挂起 3 个挑战
- 设备标识由浏览器 `localStorage` 随机生成（32 位十六进制），服务端只做比对，不参与密钥运算
- 验证码**不会**出现在接口响应里，只走推送渠道；推送失败时才降级写入本地日志（`core/data/logs`，0600）供运维排障，并明确提示用户去看日志
- 面板「系统设置 → 登录安全」可查看当前会话信息、受信任设备清单，并一键撤销全部设备
- 修改密码会同时清空所有会话与受信任设备，旧设备必须用新密码重新过验证码

**引导例外（需要你知情）**：当系统里既没有任何受信任设备、也没有活跃会话时（即该机制启用后的第一次登录，或手动撤销全部设备后又退出登录），登录会**直接放行并信任该设备**，同时推送一条「首次在该设备登录」的通知。这是无法回避的引导困境——此时没有任何"已认证过的设备"可供比对。它的代价是：如果密码在此之前就已泄露，攻击者抢先登录会被自动信任；你能依靠的是那一条立即推送的通知。

**应急开关**：`ADMIN_DEVICE_VERIFY=off` 关闭设备验证，退化为仅密码登录。仅在推送渠道坏掉、而你又恰好被挡在门外时使用，用完记得去掉。

### 哈希与找回

- 密码只以 PBKDF2（SHA-512、10 万次迭代、32 字节盐）格式存储，校验使用 `crypto.timingSafeEqual` 常量时间比较
- 早期无盐 `SHA-256` 摘要格式已**停止兼容**：这类哈希一旦泄露可被直接离线爆破，检测到只会拒绝登录，需要重设密码，不再"透明升级"
- 管理员密码丢失后的找回属于服务器运维操作，需要文件系统级访问权限，具体流程不在本公开文档中说明

### 凭据轮换

一旦怀疑 `admin.json`、`admin-sessions.json` 或 `core/data/` 曾被提交、备份外泄或截图泄露，按以下顺序处理：

1. 用新密码重算 `admin.json` 的 `password` 字段（`salt:hash` 格式，PBKDF2-SHA512/10 万次/64 字节）
2. 同时清掉 `admin.json` 里的 `trustedDevices` 字段（撤销全部受信任设备），并把 `admin-sessions.json` 重置为 `{"version":2,"sessions":[]}`，让所有已签发令牌与设备信任立即失效
3. 清空 `login-attempts.json`，避免旧锁定记录干扰
4. 重启服务使内存中的凭据缓存失效（`admin-store` 会缓存已加载的管理员记录）
5. 若旧哈希曾进入版本库，用 `git filter-repo` 从历史中抹除并强推，同时视为该密码已永久泄露

### 面板 HTTPS（内置，可选）

面板默认明文 HTTP。同网段抓包即可拿到登录密码与 `x-admin-token`，对外提供服务时应启用 TLS。

项目自带可选 HTTPS，不依赖 Nginx/Caddy：设置证书环境变量即切换为 TLS，未设置时行为与改造前完全一致。

```bash
# 1. 签发本地 CA + 服务器证书（SAN 自动包含 localhost、127.0.0.1、::1、主机名与全部内网 IPv4）
./scripts/gen-selfsigned-cert.sh

# 2. 带证书启动（在 core/ 目录下执行）
HTTPS_KEY=core/data/certs/server.key \
HTTPS_CERT=core/data/certs/server.crt \
HTTPS_CA=core/data/certs/ca.crt \
PORT=3000 node client.js
```

> 说明：上面是**前台单端口直起**的 HTTPS 特例——应用自己监听 `3000`，由它直接终结 TLS，因此不需要 `start.sh` 的 `3000 → 3007` socat 分层，也不经过看门狗。仅适合临时验证证书或证书 terminates 在本应用的场景；正式常驻请用「后台常驻运行」的 `start.sh`（此时若也要 HTTPS，把证书环境变量注入 `start.sh` 的环境即可，端口分层照常由它管理）。这条命令只手动执行，不要留在会被会话恢复重放的终端里。

| 环境变量 | 说明 |
|---|---|
| `HTTPS_KEY` / `HTTPS_CERT` | 必填且成对，缺一即拒启 |
| `HTTPS_CA` | 可选，补全证书链或用于校验客户端证书 |
| `HTTPS_PASSPHRASE` | 可选，加密私钥口令（只走环境变量，不落盘、不进日志） |
| `HTTPS_HSTS` / `HTTPS_HSTS_MAX_AGE` | 设为 `1` 才下发 HSTS，有效期默认 86400 秒 |
| `HTTPS_OPTIONAL` | 设为 `1` 时，凭据不可用降级明文而非拒启 |

行为约定：

- **配置了但不可用 → 拒绝启动**（fail-closed），绝不静默降级成明文。缺文件、私钥与证书不配对、PEM 损坏、证书过期或尚未生效，都会在启动阶段抛出可定位的错误（而非运行时才报 TLS 握手失败）
- 私钥权限宽于 `600` 只告警不阻断（避免权限设错导致面板整体不可用）；证书与 CA 属公开材料，`644` 是正常权限，不告警
- HSTS 默认**关闭**。一旦下发 `max-age`，浏览器会在有效期内强制 https，证书配错就无法再用 http 回退，因此默认只给一天且必须显式开启
- 切换到 HTTPS 后端口不变，但访问协议要改：`https://<host>:<port>`。若面板走的是 HTTP 层反向代理，切 TLS 前请先确认代理支持回源 https

自签证书的浏览器表现：未把 `ca.crt` 导入「受信任的根证书颁发机构」时，首次访问提示「连接不是私密连接」，需手动继续；导入后即正常绿锁。`ca.key` 是签发根密钥（权限 600），泄露者可签发任意站点证书，切勿外传。脚本重复执行不会覆盖已有证书，重新签发需显式加 `--force`（旧证书立即失效）。

### 部署侧加固清单

程序边界之外的安全，需要您在基础设施层完成：

- [ ] 不要将后端直连端口 `3007` 直接暴露公网；对外统一走 `3000` 入口，并启用内置 HTTPS（见上一节）或使用 Nginx/Caddy 反向代理 + HTTPS，面板路径叠加访问控制（IP 白名单或 Basic Auth）
- [ ] 公网机器部署后执行 `sudo bash scripts/firewall-harden.sh [面板端口]`：启用 ufw，仅放行 SSH 与面板端口（带连接速率限制），其余入站默认拒绝
- [ ] `core/data/` 目录包含账号凭据、会话令牌与运行数据：权限建议 700，纳入备份但绝不提交到公开仓库
- [ ] 定期审计 `core/data/logs/` 中 `admin` 模块日志，关注异常来源 IP
- [ ] 公网部署建议配置实例级事件推送（pushoo），终态掉线与异常第一时间知晓
- [ ] 新设备验证码依赖推送渠道：**推送不通 = 新浏览器登录不进来**。部署后先用一个无痕窗口验证整条流程，确认能收到验证码，再清掉无痕窗口产生的受信任设备
- [ ] 收到「面板登录」通知但确认不是本人操作时：立即改密码（会自动清空所有会话与设备信任），并检查 `core/data/logs/` 中 `admin` 模块的来源 IP
- [ ] 反向代理之后部署时设置 `TRUSTED_PROXY_IPS`，否则所有请求都会被识别为代理 IP，限流退化为全局单桶
- [ ] `.env` 权限设为 `600`；它虽然只含端口与时区，但同目录可能追加其他本地配置

### 依赖基线

传递依赖通过 `pnpm-workspace.yaml` 的 `overrides` 钉到已修版本（`proxy-addr`、`body-parser`、`qs`、`engine.io`、`socket.io-parser`、`ws`、`form-data`、`lodash`、`postcss`、`picomatch` 等），`pnpm audit --prod` 仅剩 5 项，且无 critical。

其中 **`protobufjs` 固定在 `8.0.2`（精确版本，不加 `^`）**，这是有意为之：

- `8.0.1` / `8.0.2` 修掉了远程代码执行与代码生成 gadget 两类严重问题，是本项目协议解析路径的必需基线
- `8.4` 起改变了 `toObject` 的默认值填充行为，`slot_index: 0`、`false`、`''` 这类显式零值字段会被丢弃。项目的协议层要求**逐字节复现官方抓包**（`tests/network-keepalive`、`farm-interaction-cleanup` 等 8 条断言直接用十六进制比对），升到 8.4+ 会直接破坏请求体一致性
- 未修的剩余项（`Any` 无限展开 DoS、递归 JSON DoS、`.proto` 死循环）都发生在**解析不可信输入**时；本项目的 protobuf 输入来自游戏服务端与仓库内的 `.proto` 文件，不在攻击者可控范围内

### 端口与网络

**日常使用只需记住一个地址：对外统一入口 `http://<主机地址>:3000`。** 其余端口由程序自行管理，无需关心。

| 端口 | 角色 | 说明 |
| --- | --- | --- |
| `3000` | 对外统一入口 | `start.sh` 检测到后端端口不是 `3000` 时，自动用 socat 把 `3000` 转发到后端；浏览器、反代、局域网访问一律用这个端口 |
| `3007` | 后端直连端口 | Express + Socket.IO，REST API 与 WebSocket；默认只监听 `127.0.0.1`，仅供本机排障，不要直接暴露公网；需要时可在运行配置中调整 |

前端为纯静态资源（`web/dist/`），由后端一并托管，不单独占用端口。

## 游戏资源更新（配置与图标）

游戏每次版本更新都会新增作物、动物、道具与活动条目。本地配置落后时，面板会出现三类症状：图鉴/背包里显示成「种子1046038」这类纯 ID、格子只有占位图、牧场新动物在选项里缺失。原因是服务端只下发物品 ID，**名称与图标都在客户端资源包里**，所以必须同步客户端配置。

### 方式一：从微信小程序缓存取版本（推荐，无需反编译）

微信 PC 端运行过小程序后，会把远程资源清单缓存在本地，里面有可直接读取的 bundle 版本号：

```
%APPDATA%\Tencent\xwechat\radium\users\<用户ID>\applet\local\wx5306c5978fdb76e4\usr\gamecaches\cacheList.json
```

该文件是「CDN URL → 本地缓存文件」的映射，形如：

```
https://cdn-resource.nqf.qq.com/release/remote/mainscene/config.8e8d5.json
https://cdn-resource.nqf.qq.com/release/remote/plant/config.28471.json
```

对每个 bundle 取 `lastTime` 最新的一条，即可得到 `settings.json` 需要的内容：

```json
{
  "assets": {
    "server": "https://cdn-resource.nqf.qq.com/release/",
    "bundleVers": { "mainscene": "8e8d5", "plant": "28471", "animal": "c86eb" },
    "remoteBundles": ["mainscene", "plant", "animal", "extraRes", "delayRes", "audio", "petdog", "commonRes", "mcRes"]
  }
}
```

把它放到一个空目录的 `src/settings.json`（例如 `/root/fakesrc/src/settings.json`），然后跑仓库自带工具：

```bash
# 1) 下载配置（ItemInfo / Plant / Illustrated / RoleLevel / Land / MutantEffect / BuffCfg + allconfig）
node tools/download-game-config.js --source /root/fakesrc --output /root/gc

# 2) 按配置下载图标（物品/种子/果实/牧场动物）
node tools/download-game-images.js --input /root/gc --output /root/imgs --source /root/fakesrc --concurrency 16
```

### 方式二：使用反编译源码目录

已经反编译过小程序（`wx5306c5978fdb76e4`）时，直接把源码目录传给 `--source` 即可，工具会自行读取 `src/settings*.json`：

```bash
node tools/download-game-config.js --source <反编译源码目录> --output <输出目录>
```

### 落盘与收尾

```bash
# 配置：备份后覆盖
cp core/src/gameConfig/*.json /root/gc-backup-$(date +%Y%m%d-%H%M%S)/
cp /root/gc/{ItemInfo,Plant,Illustrated,RoleLevel,Land,MutantEffect,BuffCfg}.json core/src/gameConfig/

# 图标：仅补缺失，不动已有文件，然后统一压缩
rsync -a --ignore-existing /root/imgs/ core/src/gameConfig/seed_images_named/seed_images/
pngquant --quality=70-96 --speed 3 --ext .png --force core/src/gameConfig/seed_images_named/seed_images/*.png

systemctl restart qq-farm-bot
```

启动日志会打印实际加载条数，可作为校验：

```
[配置] 已加载植物配置 (323 种)
[配置] 已加载物品配置 (1176 项)
[配置] 已加载图鉴配置 (329 项)
```

再查 `/api/illustrated`，若「无图 0、名字退化 0」即同步完成。

> [!TIP]
> - 图标目录体积可用 pngquant 压掉约 60%（22.8MB → 9.1MB），画质肉眼无损，适合经隧道/公网访问面板的场景。
> - `/game-config` 已下发 `Cache-Control: public, max-age=31536000, immutable`，图片 URL 带 `?v=<文件 mtime>` 自动失效，换图后无需手动清缓存；若前面有 Cloudflare，可先按新 URL 预热一遍边缘缓存。
> - `download-game-images.js` 报 `PATH_NOT_FOUND` 的条目属于客户端本身没有该资源，可以忽略。

## 二创变更摘要

- 移除外部 farm-code 换码 fallback：微信换码仅保留本地 loginBuffer 方式
- 微信登录 buffer 失效自动重获：无 refreshToken 时自动用 openid + accessToken 重获 loginBuffer 再换码
