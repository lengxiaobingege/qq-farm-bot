# 事件推送与掉线判定

账号掉线时"什么时候推、什么时候不推"。实现：`core/src/runtime/event-notify.ts`、`core/src/runtime/wechat-auto-relogin.ts`。

## 一、为什么不能一断就推

微信连接断开是常态：换码、心跳重连、服务端抖动都会拉断 WebSocket，绝大多数几十秒内自动回来。每次都推，一天几十条"已离线"，真正需要扫码的那次反而被淹掉。

所以改成**延迟判定**：先挂起，把时间让给自动重登，确定救不回来才打扰。

## 二、判定流程

以**掉线周期**为单位：从首次断线到连接恢复算一次周期，一个周期最多推一条。

```text
连接断开（disconnect / ws_error / kickout）
  │
  ├─ 本周期已推过？ ──是──> 只记日志（终态也不补第二条）
  │
  ├─ 终态原因？ ──是──> 立即推送，不等窗口
  │                     auto_relogin_failed / no_session / offline_timeout / kickout_limit
  │
  └─ 过程态 ──> 挂起 OFFLINE_DEFER_MS = 150 秒
                   ├─ 期间恢复 ──> 结束周期，完全静默
                   ├─ 期间转终态 ──> 立即推，清掉定时器
                   └─ 到期仍断 ──> 兜底推送（附"已等待 150 秒"）

推过"已离线"的周期，恢复时补一条"已恢复在线"，形成闭环；
没推过的周期不补——150 秒内的抖动恢复不该产生任何通知。
```

同周期内再次断线只**重置计时**（从最后一次断线重算），原因保留首次那条，避免抖动把"断线"改写成"重登失败"。

### 恢复文案区分来源

| 场景 | 判据 | 文案 |
| --- | --- | --- |
| 自动重登 / 心跳重连成功 | 周期未进终态 | 掉线约 N 分钟后**已自动重新连接** |
| 人工扫码恢复 | 周期已进终态 | 掉线约 N 分钟后**已通过扫码重新登录** |

`N` 从周期起点（首次断线）算，不是从推送时刻算。

### 谁负责通知

登录成功、扫码成功、服务重启都**不推送**——这些只说明服务在正常工作。worker 侧的登录提醒已移除，所有通知收敛到本模块：只有"确实推过掉线"，才值得在恢复时再告诉用户一次。

### 为什么是 150 秒

自动重登三次重试（30s + 12s + 30s），实测一次完整失败链约 43 秒，加上首次重试等待与换码开销，最坏约 92 秒。窗口取 150 秒留约 60 秒余量，又短于"用户开始怀疑卡死"的心理阈值。

正常失败会在 75~90 秒由终态推送接管并清定时器；150 秒这条只负责"既不成功也不失败"的卡死场景，日常几乎走不到。

## 三、不重复打扰的五个机制

| 机制 | 行为 | 目的 |
| --- | --- | --- |
| 一周期一条 | `noticeSent` 置位后，后续断线/终态只记日志 | 过程态与终态不再各推一条，也避免 pushplus 对重复内容返回 `code 999` 丢弃 |
| 成功才记账 | `noticeSent` 只在推送**送达**后置位；失败退避 30 秒重试，最多 2 次 | 老实现先记账再发，失败后既丢提醒，恢复时又冒出一条没头没尾的"已恢复在线" |
| 状态落盘 | 周期写入 `core/data/event-notify-state.json`，重启后加载（超 30 分钟的丢弃） | 重启不清空记忆，同一笔掉线不会因重启再推一遍 |
| 恢复即结束 | 连接恢复时删除周期并落盘 | 下次真掉线重新走完整流程 |
| 恢复通知节流 | 同账号 10 分钟内最多一条恢复通知 | 反复掉线/恢复只报一次 |

## 四、被挤下线：让位而不是抢登录

用户打开小程序时，服务端下发 `gatepb.KickoutNotify`（"已在其他终端登录"），bot 被踢。立刻重登只会互踢，所以走**让位阶梯**（`KICKOUT_BACKOFF_MS`，`runtime/wechat-auto-relogin.ts`）：

| 第 N 次被挤 | 重登延迟 |
| --- | --- |
| 1 | 1 分钟 |
| 2 | 3 分钟 |
| 3 | 5 分钟 |
| 4 | 10 分钟 |
| 5 及以上 | 暂停 `KICKOUT_PAUSE_MS = 30` 分钟，到期再试一次 |

配套约束：

- **计数窗口** `KICKOUT_WINDOW_MS = 30` 分钟：窗口内没再被挤就清零，第二天不继承昨天的档位
- **状态落盘** `core/data/kickout-guard.json`：记录被挤时间点、暂停截止时间、本轮让位截止时间（`yieldUntil`），重启后继续按当前档位让位，不会一重启就抢登录
- 让位类原因在提醒侧使用 `KICKOUT_YIELD_DEFER_MS = 15` 分钟作为挂起窗口，比普通掉线更久——它本来就不是故障

## 五、推送通道

通道抽象在 `services/push.ts`，底层用 [pushoo](https://github.com/imaegoo/pushoo)。设置页可选企业微信机器人、PushPlus、钉钉、Server 酱、Telegram、Bark、自定义 webhook 等；`webhook` 与 `dingtalk` 用 `endpoint`，其余用 `token`。

管理员侧的登录验证码也走这条通道（`services/admin-notify.ts`）。**没配通道时验证码发不出去**，登录会被挡住——此时看日志或走 `tools/admin-rescue.js --reset-trust`，见根 README 常见问题。
