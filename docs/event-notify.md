# 事件推送与掉线判定

本文说明账号掉线时「什么时候推、什么时候不推」的判定逻辑，以及会话保活与推送通道的工程约束。实现位于 `core/src/runtime/event-notify.ts` 与 `core/src/runtime/wechat-auto-relogin.ts`。

## 为什么不能「一断就推」

微信连接的断开是常态而非异常：换码、心跳重连、服务端抖动都会拉断 WebSocket，而绝大多数情况会在几十秒内自动重登成功。若每次断开都立刻推送，用户一天会收到几十条「已离线」，真正需要扫码的那次反而被淹掉。

因此掉线提醒改为**延迟判定**：先挂起，把时间让给自动重登，只在确定救不回来时才打扰。

## 判定流程

判定以**掉线周期**为单位：从首次断线到连接恢复算一次周期，**一次周期最多推一条提醒**。

```text
连接断开（disconnect / ws_error / kickout）
  │
  ├─ 本周期已推送过？── 是 ──> 只记日志，不再推（终态也不补第二条）
  │
  ├─ 终态原因？ ── 是 ──> 立即推送（不等窗口）
  │                        auto_relogin_failed: / no_session / offline_timeout / kickout_limit
  │
  └─ 否（过程态）──> 挂起 150 秒
                       │
                       ├─ 期间恢复在线 ──> 结束周期，完全静默
                       ├─ 期间转终态 ────> 立即推送，清掉定时器
                       └─ 到期仍未恢复 ──> 兜底推送（附「已等待 150 秒」说明）

推送过「已离线」的周期，恢复时补一条「农场已恢复在线」，形成闭环；
没推送过的周期不补——150 秒内的抖动恢复不该产生任何通知。
```

同周期内再次断线只**重置计时**（从最后一次断线重算），原因保留首次那条，避免抖动把「断线」改写成「重登失败」。

### 恢复文案区分来源

恢复通知按周期的终态与否推断来源，不再一律说「已自动重新登录」：

| 场景 | 判据 | 文案 |
| --- | --- | --- |
| 自动重登/心跳重连成功 | 周期未进终态 | 掉线约 N 分钟后**已自动重新连接** |
| 人工扫码恢复 | 周期已进终态（自动重登已放弃） | 掉线约 N 分钟后**已通过扫码重新登录** |

`N` 从周期起点（首次断线）算起，不是从推送时刻算起。

### 谁负责通知用户

登录成功、扫码登录、服务重启都**不推送**——这些只说明服务在正常工作。worker 侧的登录提醒已移除，所有通知收敛到本模块：只有「确实推送过掉线」这一件事，才值得在恢复时再告诉用户一次。

### 为什么窗口是 150 秒

自动重登自身有三次重试（30s + 12s + 30s）。实测一次完整失败链耗时 43 秒，加上首次重试前的等待与换码开销，最坏约 92 秒。窗口取 150 秒留出约 60 秒余量，同时短于「用户开始怀疑是否卡死」的心理阈值。

正常失败会在 75~90 秒由终态推送接管并清掉定时器，150 秒这条只负责「既不成功也不失败」的卡死场景，日常几乎不会走到。

## 不重复打扰

| 机制 | 行为 | 目的 |
| --- | --- | --- |
| 一周期一条 | 周期内 `noticeSent` 置位后，后续断线/终态一律只记日志 | 过程态与终态不再各推一条，也避免 pushplus 对重复内容返回 `code 999` 丢弃 |
| 成功才记账 | `noticeSent` 只在推送**送达**后置位；失败退避 30 秒重试，最多 2 次 | 以前的实现先记账再发送，失败后既丢了这条提醒，又会在恢复时冒出一条没头没尾的「已恢复在线」 |
| 状态落盘 | 周期写入 `data/event-notify-state.json`，重启后加载（超 30 分钟的丢弃） | 重启不再清空记忆，同一笔掉线不会因重启再推一遍 |
| 恢复即结束 | 连接恢复时删除周期并落盘 | 下一次真掉线重新走完整流程，不会被旧记录静默 |
| 恢复通知节流 | 同账号 10 分钟内最多一条恢复通知 | 反复掉线/恢复时只报一次，不来回刷屏 |

## 被挤下线：让位而不是抢登录

用户自己打开小程序时，服务端下发 `gatepb.KickoutNotify`（原因「已在其他终端登录」），bot 会被踢。此时立刻重登只会和用户互踢：bot 登上去把用户挤掉，用户再开又把 bot 踢掉。

因此 kickout 走**让位阶梯**，每次被挤多让一会儿：

| 第 N 次被挤 | 重登延迟 |
| --- | --- |
| 1 | 1 分钟 |
| 2 | 3 分钟 |
| 3 | 5 分钟 |
| 4 | 10 分钟 |
| 5 及以上 | 暂停 30 分钟，到期自动再试一次 |

配套约束：

- **计数窗口 30 分钟**：窗口内不再被挤就自动清零，第二天不会继承昨天的让位进度
- **状态落盘**：`data/kickout-guard.json` 记录被挤时间点、暂停截止时间与**本轮让位截止时间**（`yieldUntil`），重启后继续按当前档位让位，不会一重启就抢登录
- **让位不因重启中断**：重启会丢掉内存里的重登定时器，此时若来了普通断线（比如旧 Code 失效的 `ws_error`），重登延迟取 `yieldUntil - now` 的剩余时间，而不是退回 30 秒
- **让位期不催用户**：kickout 的判定窗口拉长到 15 分钟（最长档 10 分钟 + 5 分钟余量），让位属于预期行为，不按 150 秒窗口推「已离线」
- **暂停要说清楚**：走到暂停时才推一条，文案附「退出小程序后会自动恢复，无需扫码」，避免用户以为要重新登录

判定流程里的 `kickout_limit:` 属于终态白名单，会立即推送。

## 推送通道

- **串行队列**：登录提醒、神秘商人到货、掉线提醒可能同一刻触发，pushoo 系渠道对同 token 并发会返回「服务端验证错误」，因此所有推送进入单一队列依次发送
- **失败重试**：首次失败后等 2 秒重发一次；仍失败则保留周期状态，30 秒后再试，最多 2 次，之后放弃并写错误日志
- **配置错误只提示一次**：渠道未配 token、webhook 缺地址等问题，同一原因只写一条日志，改配置后重新校验

## 会话保活

微信会话有效期 7200 秒。系统每小时整点刷新一次，判据是「上次刷新所属的小时数与当前小时不同」，因此不会因为进程重启而重复刷新。

- 成功后静默，不占推送配额（`PUSH_SESSION_REFRESH_SUCCESS = false`）
- 失败才推送，避免用户以为一切正常
- 无可用会话时补发 `no_session:` 终态提醒，这条走立即推送路径

账号记录上新增 `wxSessionRefreshedAt` 字段，仅用于小时比较；缺失时回退到 `updatedAt` 作为基线。

## 停机抑制

改代码、重启服务、`stop.sh` 都会主动断开连接。若不加区分，每次运维都会换来一条「农场已离线」。

实际生效的是 worker 侧的判断：worker 主动停止（用户点停止、重登前的 `stopWorker`）不会进入提醒流程——`disconnect` 与 `kickout` 分支都先检查 `worker.stopping`。`stop.sh` 也是先停 worker 再退主进程，所以运维重启不会误报。

另有一组手动开关 `markRuntimeStopping` / `resetRuntimeStopping`，用于进程退出前显式抑制提醒（置位后新断线不挂起，已挂起的到期也不推，且只在本进程生命周期内有效）。注意 `SIGHUP` 不在抑制范围内：主进程已忽略该信号并继续运行，终端挂断不属于停机。

## 参数与测试

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `offlineDeferMs` | `150_000` | 延迟判定窗口，可注入 |
| `offlineDedupeMs` | `600_000` | 恢复通知节流窗口，可注入 |
| `stateFile` | `data/event-notify-state.json` | 掉线周期落盘路径；传空串禁用（测试用） |
| `NOTICE_RETRY_DELAY_MS` / `NOTICE_MAX_RETRY` | `30_000` / `2` | 推送失败后的退避重试 |
| `STALE_CYCLE_MS` | `1_800_000` | 超过 30 分钟的旧周期在重启后丢弃 |
| `SESSION_REFRESH_INTERVAL_MS` | `3_600_000` | 会话刷新周期 |

常规测试用毫秒级窗口覆盖状态机（`core/tests/event-notify-offline.test.js`、`core/tests/event-notify-cycle.test.js`，后者覆盖失败重试、周期落盘与恢复文案）；真时间验证由 `core/tests/event-notify-offline-slow.test.js` 承担，默认跳过，需要时：

```bash
SLOW_OFFLINE_E2E=1 pnpm -C core test            # 真等 150 秒，约 3 分钟
SLOW_OFFLINE_E2E=1 OFFLINE_E2E_MS=3000 pnpm -C core test   # 缩短窗口，逻辑等价（约 6 秒）
```

慢测覆盖 13 项：到点必推且只推一条、窗口内恢复不推、抖动从最后一次断线重算、终态立即推且晚到过程态不重推、停机标记抑制已挂起提醒、取消停机后恢复推送。

> 该测试的时间轴全部按窗口比例推算（`W*0.2`、`W-BUF`、`W+BUF` 等），不写死秒数，因此缩短窗口后各阶段顺序仍然成立。若新增断言，请沿用比例式写法——历史上写死 `-1000`/`+4000` 的偏移曾导致 `OFFLINE_E2E_MS=3000` 必然失败。
